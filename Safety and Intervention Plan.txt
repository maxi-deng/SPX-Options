Safety and Intervention Plan — US Index Options Portfolio Manager

My capstone is a six-agent system that screens SPX option credit spreads against my stated objectives, verifies the recommendations, analyzes market sentiment from news, and manages a paper portfolio on my instruction. The main risks in this workflow are: hallucinated or incorrect trade recommendations (strikes, prices, or greeks that don't match the real market); unintended portfolio actions such as duplicate or oversized positions; the LLM router misinterpreting my instructions; and sentiment analysis that isn't grounded in real, current news. Even in paper trading, corrupted records destroy the value of the experiment — and the same failures would mean real losses if the system were ever promoted to live use.

Guardrails. I use several layers. Tool access is partitioned: each agent touches only its own data store — the trade picker and grader read market data read-only, only the portfolio manager writes the trade log, only the sentiment agent maintains the news index, and no agent has access to any real brokerage or execution system. Output verification is handled by a dedicated grader that independently re-fetches market data and deterministically re-checks every recommendation — both against my criteria (strike width, open interest, expiry window, distance from spot, premium floor) and for hallucination (do the legs exist, do claimed prices match fresh quotes). There is deliberately no LLM in the grading path. Action constraints protect the portfolio: trades can only be added if they came from the picker, duplicates are rejected, and any add that would push open contract pairs above a hard limit of 80 is refused with a reason. Finally, the strongest guardrail is structural: there is no path in the agent graph from picked trades into the portfolio — adding or exiting always requires a separate, explicit instruction from me.

Evaluation metrics. I track the grader pass rate (target near 100%, with failures logged by check type), price drift beyond tolerance between independent data fetches (a data-quality signal), the add-trade rejection rate (evidence the guardrails fire, or that limits need retuning), router parse accuracy against my intended task, retrieval relevance and recency for sentiment, portfolio exposures versus limits (open pairs, delta, theta), and the overall escalation rate — the fraction of runs that require my review.

Human intervention. Every position change requires me, by design. Beyond that, the system defers when: the grader fails a recommendation (results are shown with the failure details and nothing proceeds); a risk limit would be breached (rejected — only I can close positions to make room); my instruction is ambiguous (the router echoes back its parsed objectives for confirmation instead of guessing); or market data looks anomalous (one-sided quotes are excluded and flagged).

How it fits together. Guardrails prevent, evaluation detects, escalation resolves. Constraints stop the known failure modes; metrics show whether those constraints are working and calibrated; and whenever a check fails or uncertainty rises, the system's one-way flow carries that signal forward to me rather than looping silently — it fails visibly, never quietly.

Trade-offs. I deliberately chose lower autonomy at the trade-approval point, where the cost of error is highest. I rejected automatic retry loops (the picker is deterministic, so retries would reproduce the same answer and mask bugs) and backtest-driven feedback (past returns don't predict future ones). I kept the agent count small for auditability.

Deployment. The paper portfolio is itself a safety mechanism — a sandbox that produces a track record. Because the guardrails sit exactly where real-money risk would live, promoting the system to live trading would change the stakes, not the architecture.
